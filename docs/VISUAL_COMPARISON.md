# Визуальное сравнение: Старый vs Новый формат

## 📊 HTTP Request Format

### POST/PUT/PATCH запросы

```
┌─────────────────────────────────────────────────────────────┐
│                    СТАРЫЙ ФОРМАТ ❌                          │
└─────────────────────────────────────────────────────────────┘

{
  "state_type": "integration",
  "name": "AddItemToCart",
  "expressions": [{
    "url": "{{base_url}}/carts/add-advertisement",
    "params": {                           ← НЕПРАВИЛЬНО для POST
      "cart_id": "{{cart_id}}",
      "advertisement_id": "{{target_advertisement_id}}"
    },
    "method": "post"
  }]
}

⚠️  Отправляет данные как query parameters: 
    POST /carts/add-advertisement?cart_id=3&advertisement_id=4


┌─────────────────────────────────────────────────────────────┐
│                    НОВЫЙ ФОРМАТ ✅                           │
└─────────────────────────────────────────────────────────────┘

{
  "state_type": "integration",
  "name": "AddItemToCart",
  "expressions": [{
    "url": "{{base_url}}/carts/add-advertisement",
    "body": {                             ← ПРАВИЛЬНО для POST
      "cart_id": "{{cart_id}}",
      "advertisement_id": "{{target_advertisement_id}}"
    },
    "method": "post"
  }]
}

✅ Отправляет данные в теле запроса:
   POST /carts/add-advertisement
   Content-Type: application/json
   { "cart_id": 3, "advertisement_id": 4 }
```

## 🗄️ MongoDB Storage Structure

### Хранение workflow

```
┌─────────────────────────────────────────────────────────────┐
│              СТАРЫЙ ПОДХОД (Монолитный)                      │
└─────────────────────────────────────────────────────────────┘

states (collection)
└── Document
    ├── _id: "abc123"
    ├── states: [...]              ← 37 states, ~500 строк
    ├── predefined_context: {...}  ← 35 переменных, ~100 строк
    └── screens: {                 ← 10 screens, ~2500 строк
            "CartOverviewScreen": {...},
            "CheckoutSummaryScreen": {...},
            ...
        }

❌ Проблемы:
   - Огромный документ (~3000 строк JSON)
   - Дублирование при обновлении screens
   - Сложно переиспользовать компоненты
   - Неэффективное использование памяти


┌─────────────────────────────────────────────────────────────┐
│              НОВЫЙ ПОДХОД (Модульный) ✅                     │
└─────────────────────────────────────────────────────────────┘

lct_efs_db/
│
├── states (collection)
│   └── Document
│       ├── _id: "abc123"
│       └── states: [...]          ← Только определения, ~500 строк
│
├── workflow_context (collection)
│   └── Document
│       ├── _id: "abc123"          ← Тот же ID что у workflow
│       ├── base_url: "..."
│       ├── user_id: 14
│       └── ... (35 переменных)    ← ~100 строк
│
└── screens (collection)
    ├── Document
    │   ├── _id: "x1"
    │   ├── workflow_id: "abc123"
    │   ├── state_id: "CartOverviewScreen"
    │   └── screen: {...}          ← ~250 строк
    │
    ├── Document
    │   ├── _id: "x2"
    │   ├── workflow_id: "abc123"
    │   ├── state_id: "CheckoutSummaryScreen"
    │   └── screen: {...}          ← ~250 строк
    │
    └── ... (всего 10 документов)

✅ Преимущества:
   - Модульная структура
   - Легко обновлять screens независимо
   - Можно переиспользовать screens между workflows
   - Эффективное использование памяти
   - Быстрее query для конкретного screen
```

## 🎯 Use Cases

### Use Case 1: Обновить только один screen

**Старый подход:**
```
1. Получить весь workflow (~3000 строк)
2. Изменить один screen в JSON
3. Сохранить весь workflow обратно
4. MongoDB обновляет весь документ
```
❌ Неэффективно: 3000 строк для изменения 250 строк

**Новый подход:**
```
1. Обновить только один screen документ
2. MongoDB обновляет один маленький документ
```
✅ Эффективно: 250 строк изменений

### Use Case 2: Переиспользовать screen в другом workflow

**Старый подход:**
```
1. Скопировать screen из JSON
2. Вставить в новый workflow
3. Поддерживать дубликаты вручную
```
❌ Дублирование кода

**Новый подход:**
```
1. Использовать тот же screen_id в другом workflow
2. Screen автоматически переиспользуется
```
✅ DRY принцип

### Use Case 3: Валидация HTTP формата

**Старый подход:**
```
Нет валидации ⟶ Неправильный формат ⟶ Ошибки в runtime
```
❌ Проблемы обнаруживаются поздно

**Новый подход:**
```
Автоматическая валидация ⟶ Предупреждения в логах ⟶ Раннее обнаружение
```
✅ Проблемы видны сразу
